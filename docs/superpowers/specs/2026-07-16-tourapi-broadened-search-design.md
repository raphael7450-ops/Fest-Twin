# TourAPI 검색 완화 설계

## 목적

기본 축제 기획안의 입력 기간에 TourAPI 축제 검색 결과가 없더라도 바로 샘플 데이터로 떨어지지 않게 한다. 같은 지역의 더 넓은 기간 축제 데이터를 보조 근거로 조회해 대시보드가 실제 TourAPI 활용 상태를 더 자주 보여주도록 한다.

## 현재 문제

현재 앱은 입력 지역과 입력 기간으로 `searchFestival2`를 조회한다. 기본 기획안은 `서울`, `2026-09-18~2026-09-20`인데 이 조건의 TourAPI 축제 결과가 0건이다. 서버 프록시와 인증키는 정상이어도 화면은 `sample-fallback`으로 보일 수 있어, 실제 TourAPI 연동을 시연하기 어렵다.

## 목표

- 입력 기간 직접 검색 결과가 0건이면 같은 지역의 연간 축제 데이터를 한 번 더 조회한다.
- 재조회 결과가 있으면 실제 TourAPI 데이터를 근거로 사용한다.
- 입력 기간 직접 일치가 아니었다는 사실을 데이터 근거 문구에 명확히 표시한다.
- 기존 `live`, `partial-fallback`, `sample-fallback` 의미를 유지한다.
- 키 없음, 네트워크 오류, 응답 구조 오류, 지역 코드 매핑 실패 시 기존 fallback 동작을 유지한다.

## 비목표

- 사용자가 검색 기간을 직접 선택하는 UI는 추가하지 않는다.
- 데이터베이스나 캐시를 추가하지 않는다.
- TourAPI 외 다른 실시간 데이터 연동은 추가하지 않는다.
- 임의의 외부 URL 프록시는 추가하지 않는다.

## 동작 설계

`getTourismContext`는 지역 코드를 찾은 뒤 두 단계로 축제 후보를 조회한다.

1. 입력 기간 검색:
   - `eventStartDate`: `plan.startDate`
   - `eventEndDate`: `plan.endDate`
2. 결과가 0건이면 같은 지역 연간 검색:
   - 기준 연도: `plan.startDate`의 연도
   - `eventStartDate`: `YYYY0101`
   - `eventEndDate`: `YYYY1231`

연간 검색에서도 결과가 없으면 기존처럼 sample fallback을 사용한다.

## 상태 표시

입력 기간 검색에서 축제와 주변 관광지 모두 충분하면 기존처럼 `live`를 사용한다.

연간 검색으로 축제 데이터를 확보한 경우에는 `partial-fallback`을 사용한다. 이때 `fallbackReason`은 다음 의미를 담아야 한다.

- 입력 기간 직접 일치 결과가 없음
- 같은 지역의 연간 TourAPI 축제 데이터를 참고함
- 부족한 항목은 기존 샘플 데이터로 보완할 수 있음

주변 관광지와 상세 정보까지 충분하면 실제 조회 데이터 비중이 높더라도, 입력 기간을 완화했기 때문에 사용자에게 오해가 없도록 `partial-fallback`으로 표시한다.

## 테스트 기준

- 첫 `searchFestival2` 응답이 0건이면 같은 지역의 연간 범위로 두 번째 `searchFestival2`를 호출한다.
- 두 번째 검색 결과가 있으면 `sample-fallback`이 아니라 `partial-fallback` 또는 실제 데이터가 포함된 컨텍스트를 반환한다.
- 두 번째 검색도 0건이면 기존 sample fallback을 반환한다.
- API 키가 없거나 프록시가 실패하면 기존 fallback 동작이 유지된다.
- 브라우저 요청 URL에는 `serviceKey`가 포함되지 않는다.

## 성공 기준

- 현재 기본 기획안에서도 서버에 `TOUR_API_KEY`가 있으면 같은 지역의 실제 TourAPI 축제 데이터를 근거로 사용할 수 있다.
- 데이터 근거 패널은 입력 기간 직접 일치가 아니라 연간 보조 검색을 사용했다는 사실을 표시한다.
- 전체 테스트와 빌드가 통과한다.
