# 제출 시연 패키지 설계

## 목적

페스트트윈(Fest-Twin)의 현재 MVP를 심사자와 협업자가 빠르게 이해하고 검증할 수 있도록 제출·시연용 문서 묶음을 정리한다. 새 기능을 추가하지 않고, 이미 구현된 TourAPI 서버 프록시, 내부 Docker 배포, 연간 검색 완화, 리포트 출력, 시나리오 저장 흐름을 한 번에 확인할 수 있게 만든다.

## 배경

현재 대시보드는 `http://192.168.55.223:18080/`에서 내부 데모로 실행 중이고, PR #1에는 TourAPI 프록시와 Docker 배포 변경이 포함되어 있다. README와 데모 검증 문서는 기능 설명을 담고 있지만, 심사자가 어떤 순서로 무엇을 봐야 하는지와 실제 서버 검증 결과가 한곳에 충분히 정리되어 있지 않다.

## 접근 방식

추천 접근은 문서 중심 제출 패키지다. 별도 UI나 서버 기능을 추가하지 않고 다음 세 문서를 정리한다.

- `docs/submission-demo-guide.md`: 심사용 5분 시연 순서, 확인 포인트, 예상 질문 답변을 한글로 제공한다.
- `README.md`: 상단에 내부 데모 주소, PR 주소, 빠른 확인 순서를 추가한다.
- `docs/demo-verification.md`: 2026-07-17 기준 서버 배포와 TourAPI 프록시 검증 결과를 갱신한다.

대안으로 앱 내부에 안내 배너를 넣을 수 있지만, 심사용 흐름은 코드 변경보다 문서가 더 안전하다. PDF나 발표자료를 만드는 방법도 있으나 현재 단계에서는 유지 관리 비용이 크다.

## 문서 구조

`submission-demo-guide.md`는 다음 흐름을 따른다.

1. 데모 접속 정보
2. 5분 시연 순서
3. 심사자가 확인해야 할 핵심 가치
4. TourAPI와 데이터 근거 설명
5. 개인정보·공공기관 검토 포인트
6. 장애 또는 데이터 부족 시 설명 방식
7. 로컬 재현과 검증 명령

README는 처음 보는 사람이 바로 접속할 수 있도록 데모 주소와 확인 순서를 앞쪽에 둔다. 기존 개발 환경과 TourAPI 설명은 유지한다.

`demo-verification.md`는 체크리스트를 유지하되 최신 검증 결과를 추가한다. 실제 인증키 값, 서버 비밀번호, SSH 비밀번호는 기록하지 않는다.

## 검증

문서 변경이므로 기능 테스트의 목적은 기존 앱이 깨지지 않았음을 확인하는 것이다.

- `npm run test`
- `npm run build`
- 서버 대시보드 `http://192.168.55.223:18080/` HTTP 200 확인
- TourAPI 프록시 `/api/tour/festivals` 응답 `resultCode=0000` 확인
