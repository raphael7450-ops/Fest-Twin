# 지역 우선 TourAPI 축제 기획 입력 설계

## 목표

Fest-Twin의 축제 기획안 입력 흐름을 “축제명 직접 입력” 중심에서 “지역 선택 후 TourAPI 축제 후보 확인” 중심으로 바꾼다. 지자체 담당자가 관할 지역을 먼저 고르고, 해당 지역의 실제 축제 데이터를 확인한 뒤 기존 축제를 선택하거나 신규 기획안을 작성하도록 만든다.

이 변경의 목적은 공모전 데모에서 TourAPI 실제 활용 지점을 더 분명히 보여주고, 공공 담당자의 업무 흐름에 맞는 B2G SaaS 경험을 제공하는 것이다.

## 배경

현재 앱은 `FestivalPlan.region`, 기간, 키워드 변화에 따라 TourAPI 프록시 조회를 수행한다. 하지만 화면의 입력 순서는 축제명, 지역, 예산, 수용 인원 중심이라 사용자가 “내가 입력한 축제명이 실제로 검색되는가”를 자연스럽게 기대하게 된다.

TourAPI의 행사/축제 조회는 지역 코드와 기간 조건이 더 안정적인 기준이다. 특히 신규 축제 기획 단계에서는 축제명이 아직 TourAPI에 존재하지 않을 수 있으므로, 지역 기반 후보 조회와 유사 축제 참고 흐름이 더 적합하다.

## 추천 접근

지역 우선 + 축제 후보 선택형 흐름을 적용한다.

1. 사용자는 먼저 개최 지역을 선택한다.
2. 사용자는 기간을 선택한다.
3. 앱은 TourAPI에서 해당 지역·기간의 축제 후보를 조회한다.
4. 사용자는 실제 축제 후보를 선택하거나 신규 기획안 작성 모드로 전환한다.
5. 선택된 축제의 이름, 주소, 좌표, 기간을 기획안에 반영한다.
6. 수요 예측, 지도, 혼잡 시뮬레이션, ROI, 리포트는 선택된 기획안 기준으로 갱신된다.

## 대안 비교

### 1. 지역 우선 + 후보 선택형

장점:
- TourAPI 실제 조회 결과가 화면에 직접 보인다.
- 지자체 담당자의 관할 지역 중심 업무 흐름과 잘 맞는다.
- 신규 축제도 같은 지역의 유사 축제를 근거로 분석할 수 있다.

단점:
- 현재 입력 폼보다 상태와 컴포넌트가 조금 늘어난다.

판단:
- Fest-Twin의 공공 데모 설득력과 데이터 활용 근거를 가장 잘 보여주므로 추천한다.

### 2. 기존 폼 유지 + 조회 상태 강화

장점:
- 구현 범위가 작다.
- 현재 구조를 거의 유지할 수 있다.

단점:
- 사용자는 여전히 축제명을 검색 조건으로 오해할 수 있다.
- 실제 TourAPI 활용이 후보 목록으로 드러나지 않는다.

판단:
- 임시 개선에는 가능하지만 데모 설득력은 약하다.

### 3. 축제명 검색 중심

장점:
- 일반 사용자 검색 서비스처럼 익숙하다.

단점:
- 신규 축제명은 TourAPI에 없을 가능성이 높다.
- 정확한 명칭이 아니면 결과가 불안정하다.
- 공공 담당자의 지역 기반 업무 흐름과 덜 맞는다.

판단:
- Fest-Twin의 목적에는 우선순위가 낮다.

## 화면 구조

기존 `축제 기획안 입력` 패널을 다음 순서로 재구성한다.

1. 지역 선택
   - TourAPI 지역 코드 목록 기반 선택 UI를 제공한다.
   - 초기값은 현재 샘플 기획안의 지역인 서울특별시로 둔다.

2. 기간 선택
   - 시작일과 종료일을 입력할 수 있게 한다.
   - 지역 또는 기간이 바뀌면 TourAPI 후보 목록을 다시 조회한다.

3. TourAPI 축제 후보
   - 입력 패널 안에 후보를 길게 펼치지 않고, `후보 보기` 버튼으로 오른쪽 슬라이드 패널을 연다.
   - 슬라이드 패널에는 조회 중, 조회 성공, 후보 없음, 샘플 보완 상태를 표시한다.
   - 후보 항목에는 축제명, 기간, 주소를 보여준다.
   - 후보를 선택하면 `FestivalPlan`의 이름, 지역, 주소, 시작일, 종료일을 갱신하고 패널을 닫는다.

4. 신규 기획안 작성
   - 실제 후보가 없거나 신규 축제를 기획할 때 사용할 수 있다.
   - 지역과 기간은 유지하고, 축제명과 예산, 수용 인원은 사용자가 입력한다.

5. 예산·수용 인원
   - TourAPI 조회 조건은 아니므로 후보 선택 아래에 배치한다.
   - 변경 시 수요 예측, 혼잡도, ROI만 즉시 갱신한다.

## 데이터 흐름

현재 `getTourismContext(plan)` 흐름은 유지하되, 화면에서 후보 조회를 더 명확히 분리한다.

- 지역 목록 조회: `/api/tour/area-code`
- 후보 축제 조회: `/api/tour/festivals`
- 후보 상세 조회: `/api/tour/detail`
- 주변 관광지 조회: `/api/tour/nearby`

새 UI는 지역·기간 기준 후보 목록을 먼저 보여주고, 선택된 후보를 `FestivalPlan`에 반영한다. 이후 기존 예측과 시뮬레이션 파이프라인은 그대로 사용한다.

## 컴포넌트 변경

### `PlanForm`

역할을 “기획안 단순 입력”에서 “지역 기반 기획안 구성”으로 확장한다.

필요 props:
- 현재 `plan`
- `onPlanChange`
- TourAPI 후보 목록 상태
- 후보 선택 핸들러
- 후보 패널 열기 핸들러

### `FestivalCandidatePanel`

TourAPI 후보 목록을 오른쪽 슬라이드 패널로 표시한다.

역할:
- 지역·기간 기준 조회 결과를 대시보드 본문과 분리해 보여준다.
- 후보가 많아도 입력 패널과 예측 화면을 지저분하게 만들지 않는다.
- 후보 선택, 닫기, 신규 기획안 유지 동작을 제공한다.

데스크톱에서는 오른쪽 슬라이드 패널로 열고, 모바일에서는 화면 전체 또는 바텀시트에 가까운 레이아웃으로 표시한다.

### 후보 조회 서비스

`tourApiAdapter.ts`에 UI 후보 목록용 함수를 추가한다.

예상 함수:
- `getTourApiAreaCodes()`
- `getFestivalCandidates({ region, startDate, endDate })`

이 함수들은 기존 `TourismContext` 변환과 분리해서, 화면의 후보 선택 UI가 더 단순하게 사용할 수 있는 형태를 반환한다.

### `App`

`App`은 지역·기간 변경에 따른 후보 조회 상태를 관리한다. 후보 선택 시 `plan`을 갱신하고, 기존 `tourApiPlanKey` 기반 관광 맥락 조회가 다시 실행되게 한다.

## 오류와 fallback

- 지역 코드 조회 실패: 기본 지역 입력을 유지하고, 데이터 근거 패널에 샘플 대체 상태를 표시한다.
- 후보 축제 0건: “해당 기간 후보 없음”을 표시하고 신규 기획안 작성 모드를 유지한다.
- 상세/좌표 부족: 후보는 선택 가능하지만 지도와 주변 관광지는 기존 fallback을 사용한다.
- TourAPI 호출 실패: 대시보드는 깨지지 않고 기존 샘플 데이터로 예측을 유지한다.

오류는 기술 메시지 대신 공공 담당자가 이해할 수 있는 문구로 보여준다.

## 테스트 계획

- 지역·기간 변경 시 후보 조회가 실행되는지 테스트한다.
- 후보 선택 시 `FestivalPlan`의 이름, 주소, 기간이 갱신되는지 테스트한다.
- 예산 변경만으로는 TourAPI 후보 재조회가 발생하지 않는지 테스트한다.
- 후보 없음 또는 API 실패 시 신규 기획안 모드와 샘플 fallback이 유지되는지 테스트한다.
- 기존 App 렌더 테스트는 새 입력 흐름의 핵심 문구를 검증하도록 갱신한다.

## 구현 범위

이번 변경은 입력 UX와 TourAPI 후보 선택 흐름에 집중한다.

포함:
- 지역 우선 입력 구조
- 시작일/종료일 입력 노출
- TourAPI 후보 목록을 오른쪽 슬라이드 패널로 표시
- 후보 선택 시 기획안 자동 반영
- 조회 상태 표시

제외:
- 사용자 계정/저장소 기반 기획안 관리
- 행정구역 시군구 세분화
- 실제 방문객 집계 데이터 연동
- 복수 행사장 비교

## 성공 기준

- 사용자가 지역을 바꾸면 실제 TourAPI 축제 후보가 화면에 나타난다.
- 후보를 선택하면 지도와 예측 지표가 선택 후보 기준으로 갱신된다.
- 신규 축제 기획도 지역 기반 유사 축제 근거를 유지한다.
- 심사자가 TourAPI 활용 흐름을 “지역 조회 → 실제 후보 → 분석 반영”으로 이해할 수 있다.
