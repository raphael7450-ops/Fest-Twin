# 수요 예측 백데이터 보강 설계

## 목적

Fest-Twin 대시보드의 핵심 주장인 "축제 수요 예측 실패를 줄인다"를 더 설득력 있게 만들기 위해 예상 방문객 산식에 공공 백데이터 근거를 추가한다. 목표는 숫자를 더 크게 보이게 하는 것이 아니라, 지자체 담당자와 심사자가 "왜 이 방문객 수가 나왔는지"를 근거 보기에서 추적할 수 있게 만드는 것이다.

## 현재 상태

- TourAPI는 지역 코드, 축제 후보, 상세 좌표, 주변 관광지를 제공한다.
- KTDB/View-T는 행사장 접근 교통 리스크 보조 근거로 연결되어 있다.
- 지역별 관광 수요 강도는 ROI의 1인당 소비 근거로 연결을 시도한다.
- 예상 방문객은 TourAPI 메타데이터, 주변 관광지, 트렌드 샘플, 사용자 입력값을 조합한 프록시 산식에 가깝다.

현재 약점은 TourAPI가 축제별 실제 방문객 수를 직접 제공하지 않기 때문에, `흥행 예측 지수`와 시간대별 수요 예측이 "실제 과거 방문자 규모"와 약하게 연결되어 보인다는 점이다.

## 우선 백데이터

### 1. 문화체육관광부_지역축제 정보

- 출처: https://www.data.go.kr/data/15143175/fileData.do
- 데이터 성격: 전국 지역축제의 축제명, 유형, 장소, 개최기간, 주기, 방식, 최초 개최연도, 예산, 방문객 수 등.
- 적용 위치: 유사 축제 기준선.
- 기대 효과: 현재 TourAPI 유사 축제 후보에 부족한 "실제 방문객 수"와 "예산 규모"를 보강한다.
- MVP 처리: 우선 파일데이터 기반 샘플/정규화 데이터셋으로 시작하고, 이후 자동 다운로드 또는 운영 배치로 전환한다.

### 2. 한국관광공사_빅데이터_지역별 방문자수_GW

- 출처: https://www.data.go.kr/data/15101972/openapi.do
- 데이터 성격: KT 내국인, SKT 외국인 이동통신 데이터를 기반으로 한 광역 및 기초지자체별 방문자 수.
- 적용 위치: 지역 방문자 기준선.
- 기대 효과: "해당 지역은 평소 같은 월/주말에 어느 정도 방문자가 들어오는가"를 수요 예측의 하한 또는 기준선으로 제공한다.
- 주의사항: 방문자는 관광객과 동일하지 않으며, 일자별 순방문자 기준이다. 광역/기초 지자체 데이터는 임의 합산하지 않는다.

### 3. 한국관광공사_관광지 집중률 방문자 추이 예측 정보

- 출처: https://www.data.go.kr/data/15128555/openapi.do
- 데이터 성격: 이동통신 기반 관광지 방문 집중률을 2018년 이후 패턴으로 분석해 향후 30일 상대 혼잡도를 예측한 값.
- 적용 위치: 계절성/시기 보정.
- 기대 효과: "행사 기간이 원래 붐비는 시즌인가"를 상대 지표로 보여준다.
- MVP 처리: 행사장 또는 주변 관광지와 매칭되는 경우에만 보조 지표로 사용하고, 매칭 실패 시 산식에서 제외한다.

## 대시보드 반영

### 흥행 예측 지수

근거 보기에서 다음 항목을 분리해 보여준다.

- 지역 방문자 기준선: 지역별 방문자 수 데이터에서 가져온 같은 월 또는 인접 기간의 방문 규모.
- 유사 축제 기준선: 지역축제 정보의 유형, 예산, 방문객 수가 유사한 축제 레코드.
- 축제 유형 보정: 먹거리, 음악, 불꽃, 전통문화, 지역특산물 등 유형별 방문 패턴 계수.
- 계절성 보정: 관광지 집중률 또는 개최 월 기준 보정.
- 사용자 입력 보정: 수용 인원, 예산, 프로그램 매력도, 운영시간.

### 시간대별 수요 예측

기존 시간대별 차트에는 총 예상 방문객만 보여주지 않고, 아래 영향 요인을 근거 패널에 표시한다.

- 지역 기준선에서 출발한 예상 일 방문량.
- 축제 유형별 피크 시간대 분포.
- 프로그램별 예상 흡인력.
- 수용 인원 초과 여부.

### 데이터 근거 패널

데이터 근거 패널에는 "실제 조회", "파일데이터 정규화", "샘플 보완" 상태를 명확히 구분한다. 방문자 수와 관광객 수의 차이, 파일데이터 최신성, 지역 매칭 실패 사유를 짧게 표시한다.

## 데이터 모델

새 컨텍스트는 `DemandBackdataContext`로 둔다.

```ts
interface DemandBackdataContext {
  status: "live" | "file-normalized" | "partial-fallback" | "sample-fallback";
  regionBaseline?: {
    region: string;
    basePeriod: string;
    visitorCount: number;
    sourceName: string;
  };
  similarFestivalBaselines: Array<{
    name: string;
    region: string;
    type: string;
    periodLabel: string;
    budgetMillionKrw?: number;
    visitors?: number;
    similarityScore: number;
  }>;
  seasonality?: {
    label: string;
    concentrationIndex: number;
    sourceName: string;
  };
  sourceDetails: MetricEvidenceSourceDetail[];
}
```

## 산식 방향

예상 방문객은 단일 상수가 아니라 다음 순서로 계산한다.

1. 유사 축제 방문객 수가 있으면 중앙값 또는 가중 평균을 기준으로 삼는다.
2. 유사 축제 방문객 수가 부족하면 지역 방문자 기준선을 사용한다.
3. 축제 유형, 예산 규모, 운영일수, 프로그램 매력도, 주변 관광지 매력도를 보정한다.
4. 행사장 수용 인원을 기준으로 비현실적인 과대 추정을 제한한다.
5. 데이터 상태가 낮으면 confidence를 `medium` 이하로 제한한다.

## 오류 및 fallback

- 지역축제 파일데이터 매칭 실패: TourAPI 후보와 기존 샘플 유사 축제 기준선을 사용한다.
- 지역별 방문자수 API 미승인 또는 오류: 지역 방문자 기준선을 제외하고 근거에 실패 사유를 표시한다.
- 관광지 집중률 매칭 실패: 계절성 보정을 적용하지 않는다.
- 모든 백데이터 실패: 현재 샘플 기반 예측을 유지하되 confidence를 낮추고 "샘플 보완"을 표시한다.

## 테스트 기준

- 유사 축제 방문객 수가 있는 경우 예상 방문객 산식에 반영된다.
- 지역 방문자 기준선만 있는 경우에도 예측이 생성된다.
- 백데이터 실패 시 대시보드가 깨지지 않고 기존 fallback이 유지된다.
- `흥행 예측 지수` 근거 보기에는 사용된 데이터셋, 조회 조건, 사용 레코드, 한계가 표시된다.
- 방문자 수를 관광객 수로 오인하지 않도록 한계 문구가 포함된다.
- 인증키, 비밀번호, 개인식별 정보는 source detail에 노출되지 않는다.

## 구현 순서 제안

1. 지역축제 정보 파일데이터 정규화 샘플 추가.
2. 유사 축제 기준선 어댑터와 테스트 작성.
3. `createForecast`에 유사 축제 방문객 기준선을 선택적으로 반영.
4. 흥행 예측 근거 drawer에 유사 축제 방문객/예산/유형 레코드 표시.
5. 지역별 방문자수 API 프록시를 별도 단계로 추가.
6. 관광지 집중률 예측은 관광지 매칭 안정화 후 후속 단계로 추가.

## 범위 제외

- 개인 단말기 단위 이동 데이터 수집.
- 실시간 군중 위치 추적.
- SNS 실시간 크롤링 자동화.
- 지역축제 파일데이터 전체 자동 갱신 파이프라인.
- 모든 지자체별 비정형 축제 통계 통합.

## 결론

가장 먼저 붙일 백데이터는 `문화체육관광부_지역축제 정보`다. 이 데이터는 축제 유형, 예산, 방문객 수를 함께 제공하므로 현재 대시보드의 "예상 방문객 수가 왜 이 정도인가"라는 질문에 가장 직접적으로 답한다. 그 다음 `지역별 방문자수_GW`로 지역 기준선을 보강하고, 마지막으로 `관광지 집중률 방문자 추이 예측 정보`를 계절성 보정으로 붙이는 순서가 안정적이다.
