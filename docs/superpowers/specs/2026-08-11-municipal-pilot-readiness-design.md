# Fest-Twin 지자체 시범운영 준비 설계

작성일: 2026-08-11  
대상 단계: 단일 지자체 시범운영  
설계 방향: 데이터와 모델의 신뢰성을 먼저 복구한 뒤 행정 업무와 운영 기반을 확장한다.

## 1. 목적

Fest-Twin을 공모전 시연용 대시보드에서 지자체 담당자가 실제 축제 기획안을 작성하고 내부 검토 자료로 활용할 수 있는 시범운영 서비스로 전환한다.

시범운영의 핵심 성공 조건은 기능 수가 아니라 다음 세 가지다.

1. 하나의 축제를 선택했을 때 모든 화면과 산출물이 같은 축제와 같은 데이터 기준을 사용한다.
2. 예측값과 권고값의 산식, 단위, 출처, 신뢰도를 담당자가 확인할 수 있다.
3. 작성, 검토, 승인, 변경 이력을 기관 권한 안에서 추적할 수 있다.

초기 운영 규모는 한 기관, 사용자 10~30명, 동시 사용자 약 10명을 기준으로 한다.

## 2. 현재 상태와 핵심 갭

현재 프로젝트는 축제 검색, 수요 예측, 혼잡 시뮬레이션, 근거 보기, 보고서, CSV, 시나리오 저장과 224개 자동 테스트를 갖추고 있다. 다만 공개 화면과 코드 및 문서를 대조한 결과 다음 문제가 시범운영을 막는다.

### 2.1 데이터 기준 불일치

- 기본 기획안은 서울세계불꽃축제지만 지도 fallback 좌표와 병목 설명은 삼성역 및 COEX 기준이다.
- 축제 선택 이후 패널마다 이전 데이터, 샘플 데이터, 새 조회 결과가 서로 다른 시점에 교체될 수 있다.
- 부산바다축제 기간 수정과 대전 0시 축제 제외가 개별 코드 조건으로 관리된다.
- 실조회, 기간 완화 조회, 지역 백데이터, 샘플 fallback이 한 분석 결과 안에서 혼합될 수 있다.

### 2.2 모델 결과 충돌

- 안전관리 요원 권고가 서로 다른 두 계산 서비스에서 산출되어 같은 화면에 63명과 3,003명처럼 충돌할 수 있다.
- 혼잡 격자 내부 점수와 명/m² 단위가 명확히 분리되지 않는다.
- 흥행지수가 100%를 초과해 수용인원 초과율과 흥행 가능성의 의미가 섞인다.
- 대피시간이 출구 폭이나 처리용량보다 위험 셀 개수에 크게 좌우되어 과장될 수 있다.

### 2.3 행정 통제 부족

- 시나리오 목록, 상세, 생성, 수정, 삭제 API에 인증과 역할 검사가 없다.
- 공유 토큰에 만료, 폐기, 기관 범위, 열람 권한이 없다.
- 승인본 잠금, 버전, 변경 사유, 검토 의견이 없다.
- 화면과 문서는 SQLite라고 표시하지만 실제 저장소는 JSON 파일이다.

### 2.4 운영 신뢰성 부족

- 자동 배포 실패가 허용되어 배포 성공 여부가 불명확할 수 있다.
- 백업과 복구 절차가 문서 중심이며 실제 자동 실행과 복구 시험 증빙이 없다.
- CSP에 `unsafe-inline`과 `unsafe-eval`이 남아 있고 CORS가 모든 `*.ts.net` 호스트를 허용한다.
- 프로덕션 의존성에 높은 등급 1건과 중간 등급 1건의 알려진 취약점이 있다.
- README의 주요 내부 문서 링크 다수가 현재 파일 구조와 맞지 않는다.

## 3. 선택한 접근법

### 3.1 권장안: 신뢰성 우선형

데이터 기준과 계산 모델을 먼저 통합하고, 이후 행정 흐름과 운영 기반을 붙인다. 담당자가 숫자를 신뢰할 수 없는 상태에서 로그인이나 결재 기능을 먼저 추가해도 실제 검토 도구가 될 수 없기 때문이다.

### 3.2 검토한 대안

- 행정업무 우선형: 업무 형태는 빠르게 갖출 수 있지만 현재 수치 충돌이 그대로 남는다.
- 예측모델 우선형: 장기적으로 유리하지만 실제 방문객 학습 데이터 확보 전에는 시범운영 시작이 늦어진다.

## 4. 데이터 기준 통합

### 4.1 분석 기준 묶음

모든 분석은 단일 `FestivalAnalysisContext`를 입력으로 사용한다. 이 객체는 다음 정보를 함께 보관한다.

- 축제 고유 ID, 명칭, 지역, 주소
- 시작일, 종료일, 운영시간
- 위도, 경도와 좌표 출처
- 수용인원, 예산, 프로그램, 시설
- TourAPI, 교통, 기상, 관광소비, 검색 관심도, 지역축제 백데이터
- 데이터별 상태, 기준 시각, 조회 시각, 유효기간, 출처 URL
- 분석 모델 버전과 분석 실행 시각

축제 ID는 분석 전체의 최상위 키다. 지도, 예측, 안전, 근거, CSV, 인쇄 보고서는 별도 축제 정보를 조합하지 않고 동일한 분석 기준 묶음을 참조한다.

### 4.2 원자적 분석 갱신

기획안 입력과 확정 분석 결과를 분리한다.

1. 담당자가 입력값을 변경하면 화면은 `초안 변경됨` 상태가 된다.
2. 필요한 데이터 조회를 하나의 분석 요청 단위로 수행한다.
3. 모든 필수 데이터가 준비되거나 fallback 결정이 끝나면 새 분석 스냅샷을 생성한다.
4. 대시보드 전체가 새 스냅샷으로 한 번에 전환된다.

조회 중에는 이전 분석 결과를 새 축제 결과처럼 표시하지 않는다. 이전 결과를 유지해야 한다면 축제명과 기준 시각을 고정하고 `새 분석 준비 중`임을 명확히 표시한다.

### 4.3 데이터 상태 모델

데이터 항목별 상태는 다음 네 가지로 제한한다.

- `live`: 현재 조건으로 실제 조회 완료
- `cached`: 유효기간 안의 마지막 성공 자료 사용
- `supplemented`: 실제 자료 일부에 검증된 보완 자료를 결합
- `unavailable`: 분석에 사용할 수 없음

샘플 데이터는 공개 데모 모드에서만 허용한다. 시범운영 모드에서는 샘플이 필요한 핵심 지표를 `산출 불가`로 처리하거나 관리자가 승인한 보완 자료만 사용한다.

### 4.4 축제 정정 및 운영상태 관리

축제별 코드 예외를 제거하고 별도 정정 데이터로 관리한다.

- 원본 축제 ID와 원본 출처
- 공식 명칭과 표준화 명칭
- 공식 기간과 개최 상태
- 취소, 폐지, 일정 미확정 상태
- 정정 사유, 확인일, 확인자, 공식 출처 URL
- 적용 시작일과 종료일

정정은 원본 데이터를 덮어쓰지 않고 분석 시 우선 적용한다. 변경 이력은 감사 대상이다.

## 5. 예측 및 안전 모델 통합

### 5.1 공통 결과 계약

각 지표는 값만 반환하지 않고 다음 필드를 함께 반환한다.

- 표시 값과 단위
- 허용 범위
- 계산식 ID와 모델 버전
- 사용한 입력값
- 신뢰도와 신뢰도 사유
- 데이터 상태
- 경고 및 산출 제한 사유

화면, 근거 Drawer, CSV, 인쇄 보고서는 이 공통 결과를 그대로 사용한다.

### 5.2 수요와 흥행 지표

- 흥행 가능성은 0~100점으로 제한한다.
- 예상 방문객 대비 수용인원 비율은 별도의 `수용 압박률`로 표시한다.
- 실제 실적이 없는 경우 `사전 예측`, 유사 축제 실적을 사용한 경우 `유사사례 보정 예측`, 동일 축제 실적을 사용한 경우 `실적 보정 예측`으로 구분한다.
- 입력 근거가 약하면 단일 정밀 숫자와 함께 예측 구간을 제공한다.

### 5.3 혼잡 및 안전 지표

- 격자 내부 상대 혼잡 점수와 명/m²를 별도 타입과 단위로 관리한다.
- 명/m² 환산에는 면적, 시간대 체류인원, 분산계수를 사용하며 범위 검사를 적용한다.
- 안전요원 권고는 하나의 서비스에서만 산출한다.
- 대피시간은 인원, 출구 수, 출구별 유효 폭, 단위 폭당 처리량, 이동거리를 기반으로 계산한다.
- 행사장 구조 입력이 부족하면 확정값 대신 권고 범위와 낮은 신뢰도를 표시한다.

### 5.4 모델 검증

- 동일 분석 ID의 동일 지표가 화면, CSV, 보고서에서 같은지 계약 테스트로 검증한다.
- 단위가 다른 값을 합산하거나 비교하지 못하도록 타입과 런타임 검사를 둔다.
- 물리 범위 밖 결과는 사용자에게 노출하지 않고 분석 오류로 기록한다.
- 행사 종료 후 실제 방문객, 피크 시간, 사고 및 의료 건수, 교통량을 입력해 예측 오차를 저장한다.
- 첫 시즌 종료 후 지역 및 축제 유형별 오차를 분석해 모델 버전을 갱신한다.

## 6. 행정 업무 흐름

### 6.1 역할

- 담당자: 기획안 작성, 축제 검색, 분석 실행, 수정본 제출
- 검토자: 근거 확인, 검토 의견 작성, 보완 요청, 승인
- 관리자: 기관 및 사용자 관리, 데이터 정정, 최종본 잠금, 감사기록 조회

### 6.2 기획안 상태

`작성 중 -> 분석 완료 -> 검토 요청 -> 보완 요청 또는 승인 -> 최종 확정`

승인 이후 원본은 수정할 수 없다. 변경이 필요하면 이전 버전을 기준으로 새 버전을 생성하고 변경 사유를 입력한다.

### 6.3 버전과 문서 추적

각 버전은 다음 정보를 보관한다.

- 입력 기획안과 선택 축제 기준
- 분석 스냅샷과 모델 버전
- 데이터 출처 및 기준 시각
- 작성자, 검토자, 승인자
- 상태 변경 시각, 의견, 변경 사유
- 보고서 문서번호와 버전

CSV와 인쇄 보고서에도 문서번호, 버전, 상태, 분석 기준 시각을 표시한다.

### 6.4 공유 정책

- 기본 공유는 같은 기관의 로그인 사용자에게만 허용한다.
- 외부 공유는 관리자가 허용한 경우에만 생성한다.
- 외부 공유 링크는 읽기 전용이며 만료일과 즉시 폐기 기능을 갖는다.
- 토큰 원문은 저장하지 않고 해시로 검증한다.
- 열람, 다운로드, 승인, 반려, 수정, 삭제를 감사기록에 남긴다.

### 6.5 첫 화면

첫 화면은 단일 축제 분석 결과보다 업무 대기열을 우선한다.

- 내 기획안
- 검토 대기
- 보완 요청
- 최근 확정본
- 데이터 연동 상태 및 운영 공지

기획안을 선택하면 현재의 요약, 기획, 예측, 현장, 근거, 리포트 화면으로 이동한다.

## 7. 시스템 운영 구조

### 7.1 저장소

시범운영 저장소는 PostgreSQL을 사용한다. 주요 테이블은 다음 책임으로 분리한다.

- 기관 및 사용자
- 역할과 권한
- 축제 원본 및 정정 이력
- 기획안 및 기획안 버전
- 분석 스냅샷과 지표 결과
- 검토 의견과 상태 이력
- 공유 링크
- 감사기록

모든 업무 데이터에 기관 ID를 포함하고 서버에서 기관 범위를 강제한다. JSON 저장소는 개발용 fixture 또는 마이그레이션 입력으로만 남긴다.

### 7.2 인증과 보안

- 비밀번호는 Argon2id로 해시하여 저장한다.
- 인증은 서버 저장 세션과 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키를 사용한다.
- 로그인 실패 제한, 30분 미사용 세션 만료, 로그아웃 후 세션 폐기를 적용한다.
- 모든 시나리오 쓰기 API와 기관 데이터 조회 API에 인증 및 역할 검사를 적용한다.
- CORS는 환경변수 기반 명시적 허용 목록으로 제한한다.
- CSP의 `unsafe-inline`과 `unsafe-eval`을 제거한다.
- 프로덕션 의존성 취약점을 해소하고 CI에서 높은 등급 취약점을 차단한다.
- 컨테이너는 일반 사용자 권한으로 실행하고 전용 상태 점검 경로를 제공한다.

### 7.3 외부 API 장애 처리

각 데이터 커넥터는 성공 자료, 기준 시각, 유효기간, 오류 상태를 저장한다.

- 유효기간 안의 마지막 성공 자료는 `cached`로 사용한다.
- 유효기간이 지난 자료는 담당자 확인 없이 핵심 지표에 사용하지 않는다.
- 핵심 입력이 없으면 관련 지표만 산출 중단하고 다른 업무는 계속할 수 있게 한다.
- 장애와 fallback 결정은 감사기록과 운영 로그에 남긴다.

### 7.4 환경과 배포

- 개발, 검증, 시범운영 환경을 분리한다.
- 배포 전 테스트, 빌드, DB 마이그레이션 검증, 문서 링크 검사, 보안 감사, 핵심 화면 검사를 수행한다.
- 검증 실패 시 배포하지 않는다.
- 새 배포의 상태 점검이 실패하면 이전 버전을 유지하거나 자동 복구한다.

### 7.5 백업과 복구

- PostgreSQL 매일 자동 백업, 30일 보관
- 감사기록 1년 보관
- 배포 직전 데이터베이스 백업
- 월 1회 복구 시험과 결과 기록
- 데이터 손실 허용 목표 24시간 이내
- 서비스 복구 목표 4시간 이내

### 7.6 지도와 폐쇄망

인터넷 사용 시범운영에서는 VWorld를 유지한다. 완전 폐쇄망 GIS는 실제 도입 기관의 요구가 확인된 뒤 별도 프로젝트로 분리한다. 지도 사용이 불가능한 경우에도 주소, 좌표, 시설, 병목 정보는 텍스트와 표로 사용할 수 있어야 한다.

## 8. 오류 처리와 사용자 안내

- 분석 요청마다 ID를 부여해 화면 오류와 서버 로그를 연결한다.
- 사용자 메시지는 실패한 데이터, 영향받는 지표, 재시도 가능 여부를 설명한다.
- 일부 데이터 실패가 전체 화면 오류로 번지지 않게 지표 단위로 격리한다.
- 저장 실패를 성공으로 표시하지 않는다. 로컬 임시 저장과 서버 저장을 명확히 구분한다.
- 승인 및 보고서 생성 시 핵심 데이터가 오래되었거나 산출 불가인 경우 확인 절차를 거친다.

## 9. 시험운영 합격 기준

### 9.1 데이터와 모델

- 축제 변경 후 모든 패널, CSV, 보고서의 축제 ID, 기간, 주소, 좌표가 일치한다.
- 동일 지표는 모든 출력에서 같은 값과 모델 버전을 사용한다.
- 모든 주요 수치에 출처, 기준 시각, 데이터 상태, 신뢰도가 있다.
- 단위 오류와 물리 범위 밖 결과는 자동 차단된다.
- 안전요원, 밀집도, 대피시간은 하나의 승인된 계산 경로만 사용한다.

### 9.2 행정 기능

- 담당자, 검토자, 관리자 권한이 분리된다.
- 무권한 조회, 수정, 삭제가 차단된다.
- 승인본은 잠기고 변경 시 새 버전과 변경 사유가 생성된다.
- 검토 의견과 상태 변경을 사용자 및 시각 기준으로 추적할 수 있다.

### 9.3 운영

- 외부 API 장애 중에도 유효한 저장 자료로 허용된 업무를 지속할 수 있다.
- 백업본으로 4시간 이내 복구할 수 있다.
- PC와 태블릿에서 핵심 업무를 완료할 수 있다.
- 키보드만으로 주요 입력, 검토, 승인 기능을 사용할 수 있다.
- 배포 검증 실패가 시범운영 환경에 반영되지 않는다.

### 9.4 예측 정확도

첫 시범 시즌에는 임의의 정확도 수치를 보장하지 않는다. 실제 행사 결과를 저장하고 다음 지표를 산출할 수 있는 상태를 합격 기준으로 삼는다.

- 총 방문객 절대 오차와 오차율
- 피크 시간 오차
- 시간대별 수요 오차
- 혼잡 위험 구간 적중 여부
- 의료 및 안전 권고 대비 실제 운영 결과

## 10. 단계별 도입 범위

### 1차: 신뢰성 복구

- 분석 기준 묶음 도입
- 축제 선택 시 원자적 갱신
- 지도 좌표와 병목 설명의 축제 종속화
- 안전 및 수요 모델 통합
- 데이터 상태와 신뢰도 표시
- 축제 정정 및 운영상태 데이터 분리
- 문서 링크와 저장소 설명 정합성 복구

### 2차: 행정 기능

- PostgreSQL 스키마 구축과 기존 JSON 시나리오 이전
- 로그인과 기관별 역할
- 기획안 상태 흐름
- 검토 의견, 승인, 보완 요청
- 버전 관리와 확정본 잠금
- 제한된 공유와 감사기록
- 업무 대기열 중심 첫 화면

### 3차: 운영 전환

- PostgreSQL 운영 설정과 마이그레이션 자동 검증
- 자동 백업과 복구 시험
- CSP, CORS, 컨테이너, 의존성 보안 강화
- 환경 분리와 실패 차단 배포
- 데이터 연동 상태와 운영 모니터링

## 11. 즉시 해결 대상

1. 서울세계불꽃축제에 남아 있는 삼성역, COEX 좌표와 설명

3. 흥행지수 100% 초과와 운영점수 의미 혼용
4. 분석 데이터 로딩 전후 수치 변경을 알리지 않는 동작
5. 인증 없이 전체 시나리오를 조회, 수정, 삭제할 수 있는 API
